## Question

At 30 fps, does a **1.67 s** action chunk (k=50) or a **3.33 s** chunk (k=100) fit this task better?

The ACT paper's ablation peaks at k=100 **at 50 Hz** — 2.0 seconds. We record at 30 fps, so the paper's optimum in *time* terms is **chunk 60**. That puts k=50 slightly short and k=100 well past it. Running both brackets the answer instead of assuming it.

Chunk size is the **only** axis that differs between the two array tasks.

## Dataset

[`saimaligi/pen_pick_and_place_20260817_162529`](https://huggingface.co/datasets/saimaligi/pen_pick_and_place_20260817_162529) — public, LeRobotDataset v3.0.

| | |
|---|---|
| Episodes | **60** |
| Frames | **32,032** (17.8 min) |
| fps | 30 |
| Cameras | 3 × 480×640 (AV1) |
| State / action | 6-dim, `so_follower` |
| Task strings | **1** — `"pick up the pen and place it in the container"` |
| Episode length | min 13.0 s · median 18.0 s · max 24.5 s |

It contains **learning-from-failure episodes**: the arm misses, then recovers, and *every episode ends with the pen correctly placed* (confirmed by Yash, 2026-09-05).

That distinction is the one that matters. ACT's loss is L1 on demonstrated actions — the gradient always pulls **toward** the data and there is no "avoid this" signal. An episode ending in failure would make the policy *more* likely to reproduce that failure. These end in success, so they are DAgger/RaC-style **positive supervision at off-distribution states**, which is exactly what we want. Same reasoning as [`phi_so101_cubes_cylinder_recovery_v1`](../datasets/phi_so101_cubes_cylinder_recovery_v1.md).

## Three findings from inspecting the data before training

### 1. 🚨 The camera keys are rotated by one

Verified 2026-09-05 by decoding frames from all three streams:

| Key in the dataset | What the footage actually shows |
|---|---|
| `observation.images.front` | **wrist** — gripper jaws in frame, pen close up |
| `observation.images.top` | **front** — arm side-on, table edge, box at right |
| `observation.images.wrist` | **top** — downward view over the workspace |

**Training is unaffected.** ACT does not care what the channels are called; it fits whatever is in them, and all three streams are present for every episode.

**Deployment is not.** At inference `SOFollower` writes the physical wrist camera into `observation.images.wrist`, which during training carried the *top* view. The policy then gets the wrong image on every channel and fails silently, with no error and no warning — the same failure signature as the calibration bug of 2026-08-10.

⇒ **Any rollout must remap the keys, or the dataset must be re-uploaded with them corrected.** Same bug class as [`phi_so101_8bin_v1`](../datasets/phi_so101_8bin_v1.md) (see [2026-08-04](2026-08-04_act-8bin-6run.md)), though that one was a two-way swap and this is a three-cycle.

### 2. 🚨 This data is in Sai's calibration frame

A policy trained here emits joint angles in the frame of the arm as Sai had it calibrated on 2026-08-17 — **not** `configs/calibration/robots/so_follower/phi_follower.json`. Running it against a different calibration mis-grasps silently. Get Sai's calibration file before any rollout. See `docs/robots/so-arm101/02-setup.md §3c`.

### 3. The recovery episodes are not labelled, and length does not separate them

`total_tasks == 1`, so nothing in the metadata distinguishes recovery from clean. Length is a weak proxy here: the distribution is **continuous** from 13.0 s to 24.5 s, unlike the cubes/cylinder set where recovery episodes formed a clear cluster (21.8 s vs 18.6 s clean). The seven longest are `[0, 7, 20, 25, 26, 32, 37]` — **scattered, not a trailing block**.

Consequence: the holdout below is **not stratified** by recovery-vs-clean, and it happens to draw from a shorter-than-median tail (episodes 48–59 average 15.4 s vs 18.0 s overall). Read the eval numbers with that in mind.

| Batch / steps | 8 / 100,000 |

| Hardware | Explorer `gpu` partition, 1 GPU, 8 h wall |

**On `eval_split`.** `make_train_eval_datasets` holds out `ceil(n * eval_split)` per task string. For n=60 we want 12, which needs `0.18334 < s ≤ 0.2`. `0.2` sits exactly on the boundary (`60*0.2 == 12.0`); **0.195** gives 11.7 and is safely inside. The same rounding trap is documented in [`train_recovery.sbatch`](../configs/hpc/train_recovery.sbatch).

## Infrastructure — two failures worth writing down

**`/scratch/gupta.yashv/phi` was found empty**, and no conda env survived with it. Scratch is purged on Explorer; nothing durable can live there.

**So the env was pointed at `$HOME` — and that failed too.** Build `9989313` died after 8 min with the log truncated mid-write, empty stderr, exit 1. Not OOM: `MaxRSS` was 12.7 GB against 32 GB requested. The cause was **`Disk quota exceeded`**, confirmed by a direct `dd` test.

The trap is that the quota is **invisible to the usual tools**. `quota` returns `Operation not permitted`, and both `df -h $HOME` and `statvfs` report the *shared* filesystem — 255 T with 110 T free — not the per-user cap. The only reliable probe is trying to write.

Home breakdown at the time (~77 GB, which is where it bites):

| | |
|---|---|
| `microDLM` | 27 G |
| `.conda` (4 envs + the 7.8 G partial) | 26 G |
| `.cache` | 19 G |
| `.local` | 4.8 G |

A complete `phi-cuda` env needs ~11 GB, so home cannot hold it without evicting real work.

**Resolution: env, HF video cache and checkpoints on `/scratch`; scripts and logs in `$HOME`.** The purge risk is answered by making rebuild cheap rather than by fighting the quota — [`build_env.sbatch`](../configs/hpc/build_env.sbatch) is in git and takes ~10 min, so recovering from a purge is one `sbatch`. That is a better trade than a 27 GB eviction. To use home instead, free ~15 GB (`.cache` is the softest target) and flip `ENV_PREFIX` back.

The build runs on a compute node — the login node kills `conda create` — with a **job-local `$HOME`** so conda gets a clean pkgs cache. `CONDA_PKGS_DIRS` and `CONDARC` only *merge* into `pkgs_dirs`; they do not replace it, which is why the cache-corruption workaround has to be a fake `$HOME`.

torch is pinned to the **cu126** wheel. Explorer GPU nodes run driver 545.23.08 (CUDA 12.3); a cu130 build fails with `driver is too old` and `cuda.is_available() == False`.

### A third failure: `~/.local` shadows the env

Array `9989528` split: task 0 died in 1 s with `ImportError: libnvJitLink.so.12`, task 1 ran — **on the wrong torch**, reporting `built for 12.1` instead of our `2.11.0+cu126`.

Cause: `~/.local/lib/python3.12/site-packages/torch` is a 1.6 GB cu121 install that **takes precedence over the env's**. Putting `$ENV_PREFIX/bin` on `PATH` does not prevent it; only `PYTHONNOUSERSITE=1` does. Proven directly:

```
env python                    -> ImportError: libnvJitLink.so.12
PYTHONNOUSERSITE=1 env python -> /scratch/.../phi-cuda/.../torch  2.11.0+cu126
```

The dangerous half is task 1: it did not crash, it trained on an unpinned stack. A silent wrong-version run is worse than a failed one.

**This was already solved in this repo** — all 18 other `configs/hpc/*.sbatch` set `PYTHONNOUSERSITE=1`, several with a comment naming the exact cause. It was missed when adapting the template. Fixed in `train_pen_act.sbatch`; cancelled and resubmitted as `9989698`.

## What these two numbers can and cannot tell you

**CAN** — *does a 1.67 s or a 3.33 s chunk fit this task better?* The holdout is identical across both tasks, so `eval_loss` is directly comparable. This is the question the run was launched to answer.

**CANNOT** — *which chunk is better on the robot?* Held-out L1 on teleop data is not success rate, and the ordering can invert. [2026-08-12](2026-08-12_dp-recovery-encoder-ab.md) is the cautionary case: a checkpoint whose held-out loss rose 4× matched a 100k-step ACT model on the arm. **Score rollouts.**

**CANNOT** — *did it learn to recover?* The holdout contains no induced failure, so nothing in it tests recovery. That needs a rollout protocol where you deliberately displace the pen mid-episode and count re-approaches. Separate work, and it is the actual gate on whether the failure episodes paid for themselves.
