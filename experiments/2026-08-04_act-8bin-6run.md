# ACT on 8-bin v1 — camera set × action chunk (6 runs)

**Status**: Training launched 2026-08-04 · **Owner**: Yash · **Array**: `8935891` on Explorer
**Dataset**: [`BrutalCaesar/phi_so101_8bin_v1`](../datasets/phi_so101_8bin_v1.md) — 119 eps, 72,518 frames, public
**Config**: [`configs/hpc/train_8bin_v1.sbatch`](../configs/hpc/train_8bin_v1.sbatch) · **Cluster notes**: [hpc/explorer](../docs/hpc/explorer.md) · **Architecture**: [act-shapes](../docs/theory/act-shapes.md)

## Goal

Does adding a **front** or a **top** view to the wrist camera help more, and does a longer **action chunk** help or hurt? Measured by success rate on **two bin positions never seen in training**.

## The grid

Two camera sets × three chunk sizes. **No augmentation** — deferred by decision on 2026-08-04 to keep this at 6 runs; it stays a planned later axis.

| Task | Cameras (physical) | Dataset keys | chunk | Open-loop horizon |
|---|---|---|---|---|
| 0 | wrist + top | `top` + `wrist` | 50 | 1.67 s |
| 1 | wrist + top | `top` + `wrist` | 75 | 2.50 s |
| 2 | wrist + top | `top` + `wrist` | 100 | 3.33 s |
| 3 | wrist + front | `top` + `front` | 50 | 1.67 s |
| 4 | wrist + front | `top` + `front` | 75 | 2.50 s |
| 5 | wrist + front | `top` + `front` | 100 | 3.33 s |

> 🚨 **The dataset's `wrist` and `top` keys hold each other's footage.** Physical wrist is stored as `top`, so **both** sets include `top`. Not a typo — see the [dataset card](../datasets/phi_so101_8bin_v1.md). `sanity_check_dataset_robot_compatibility` does not detect this.

Camera selection uses `--policy.input_features`, which survives `make_policy` (guarded by `if not cfg.input_features`), so no derived datasets and no duplicated video.

## Split

**89 train / 30 held out.** Left bin 3 (eps 29–43) and right bin 2 (eps 74–88) are excluded from training entirely and used as out-of-distribution eval positions. Train indices: `0–28, 44–73, 89–118` — **post-deletion** numbering (original ep 18 is gone; everything after shifted down one). The job asserts the split is exactly 89 episodes with zero overlap and aborts otherwise.

## Config, and why

Measured on **V100-SXM2-32GB**, 2 cameras, chunk 100, pyav (bench `8935610`):

| Batch | `updt_s` | `data_s` | steps/s | `smpl/s` | VRAM |
|---|---|---|---|---|---|
| 16 | 0.299 | 0.005 | 3.29 | 53 | 6.91 GB |
| 32 | **0.577** | **0.009** | **1.71** | **55** | **13.20 GB** |
| 48 | 0.851 | 0.012 | 1.16 | 56 | 19.49 GB |

- **`smpl/s` is flat** (53→56 for 3× the batch): the GPU saturates at batch 16, so **wall time tracks samples processed, not batch size**. Batch 48 buys +1.8% throughput for +48% VRAM.
- **VRAM is linear**: `0.62 GB + 0.393 GB/sample` → batch 71 would fit. Memory is not a constraint.
- **`data_s = 0.009 s`** → pyav decode is fully hidden behind the GPU step. Video decoding is free here.

| Setting | Value | Reason |
|---|---|---|
| `batch_size` | **32** | at the throughput plateau; matches the earlier Ava config |
| `steps` | **34,000** | = **20 epochs** over 54,770 frames = **5.5 h**, leaving 2.5 h of the 8 h wall |
| `save_freq` | 5,000 | 7 checkpoints to choose from |
| `seed` | 1000 | Φ rule |
| `num_workers` | 8 | `data_s` ≈ 0 **on the V100 this was benched on** — but see the finding below: on an H200 this is too few |
| `video_backend` | `pyav` | torchcodec cannot load on Explorer — see [hpc/explorer](../docs/hpc/explorer.md) |

**How 20 epochs was chosen — there is no formula.** LeRobot's own default is `100k steps × batch 8` = **14.6 epochs** on this dataset. Matching the Ava plan would be ~26 epochs but leaves only 48 minutes of wall, and one checkpoint stall eats that. Runs resume from `last`, so **under-shooting costs one resubmission while over-running the wall loses the entire run** — that asymmetry, not a learning argument, sets the number.

⚠️ **Honest limit on the batch choice:** loss at step 300 barely separates the batch sizes (2.74 / 2.44 / 2.34), and 300 steps says nothing about final quality. Batch 32 rests on convention and GPU utilisation, not on evidence that it trains better here.

## Finding during the run: workers, not the GPU

Tasks 1 and 2 landed on **H200s**, where `updt_s` fell to 0.114 s and `data_s` rose to **0.131 s** — decode became the ceiling and half the GPU sat idle (4.08 steps/s where ~8.8 was available). The V100 tasks kept `data_s ≈ 0.005` with the identical pipeline. Nothing changed but the GPU speed.

Left alone deliberately: the H200 runs finish in ~2.3 h against an 8 h wall, so the loss is free, and `num_workers` affects speed only — never results. **The next batch (Sai, Parv) should use `--cpus-per-task=16 --num_workers=16`.** Mechanism and limits: [hpc/explorer](../docs/hpc/explorer.md#reading-the-throughput-numbers).

**Task 3 was cancelled and resubmitted** (array `8936441`) after landing on `c2207`, a Zen-1 node whose host CPU made it 3× slower (`updt_s` 1.712 vs 0.570, 17 vs 55 smpl/s) — 17.5 h for a 34k-step run, so the 8 h wall would have killed it at ~45%. No checkpoints existed yet, so nothing was lost but 36 min. `c2204–c2207` are now excluded; GPU choice does not affect results, only speed, so tasks 0–2 remain comparable.

Also measured: a **QOS cap of 4 concurrent jobs per user**, so a 6-task array runs 4 + 2, not 6 at once. And ~7 min of startup per task (three cold torch imports in `_preflight.sh` plus dataset metadata) — worth collapsing into one Python process.

## Eval protocol

**Report success rate per held-out bin, never averaged.** With 15 eval episodes per bin a single success is 6.7%, and averaging the two bins throws away the left-vs-right comparison the design exists to make. Use the progress score from the [wrist-only experiment §6.2](2026-07-30_act-wrist-only-so101.md) (0.2 reached / 0.4 grasped / 0.7 at container / 0.8 released / 1.0 in container).

⚠️ **Left bin 3 and right bin 2 are not equally difficult.** Block A episodes carry ~3–4 s of leading dead time and average 22–24 s; block B averages 17–19 s. They differ in *data quality* as well as position, so a model doing better on right bin 2 may be telling you about dead time, not spatial generalisation.

⚠️ **Checkpoint selection cannot use eval loss.** All 30 held-out episodes are reserved for robot eval, so there is no validation split and the only loss available is training loss. Pick by **robot rollout** across the 7 checkpoints, not by any curve.

## Command

```bash
sbatch configs/hpc/train_8bin_v1.sbatch     # array 0-5, one GPU each
```

`--gres=gpu:1 --exclude=d1025` keeps every task eligible for H200, A100 and both V100 variants at once — d1025 (T4, 16 GB) is the only sub-32 GB node in the `gpu` partition, and node features are `(null)` so `--constraint` is useless. W&B logs **online** (`--wandb.project=phi-act`); the job falls back to `offline` + sync if no credential exists.
